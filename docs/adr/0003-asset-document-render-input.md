# ADR-0003：资产文档作为唯一渲染输入

- 状态：已接受
- 日期：2026-10-11
- 决策人：项目负责人

## 背景

M1 的渲染输入由 `parse_first_mesh_primitive` 提供：它在适配器内部递归查找默认场景中的首个 mesh 节点，用 `glam` 累乘世界变换，返回一个**拥有几何数据**的 `MeshInstance`。

M2-001 与 M2-002 建立了 `AssetDocument`（场景、节点、多个 mesh primitive、材质、纹理与统计），但渲染器仍走旧入口，由此产生三个问题：

1. **两个解析入口**：同一份字节经两条路径产出两种模型，属性数量校验等不变量必须在两处维护，属于"修一处漏一处"的结构性风险。
2. **职责错位**：场景遍历与世界变换组合属于资产语义，却写在格式适配器里；渲染器消费的实例拥有几何，与文档中已存在的几何形成潜在的第二份真相。
3. **渲染输入未表达 v0.1 范围**：多节点、多 primitive、材质与纹理在解析侧已经可用，渲染侧仍只有"首个 primitive"。

## 决策

1. **`AssetDocument` 成为渲染器的唯一数据来源。** 渲染器不再接收适配器构造的拥有式实例，而是消费 Core 派生的网格实例视图。
2. **实例视图是"借用 + 计算值"的混合体。** 几何借用文档（零拷贝）；世界变换是遍历时计算出的值，无物可借，只能按值持有：

   ```rust
   pub struct MeshInstance<'a> {
       pub mesh: &'a MeshData,
       pub world_transform: [[f32; 4]; 4],
   }
   ```

3. **场景遍历与世界变换组合归 Core。** `AssetDocument::mesh_instances` 遍历默认场景，规则为：按场景声明序、深度优先、子节点按声明序；被多个父节点引用的节点只访问一次；局部变换按 glTF 的 `M = T * R * S` 组合后与父世界矩阵相乘。
4. **遍历顺序是契约，不是实现细节。** 顺序决定"第一个实例是谁"，进而决定渲染结果与将来的诊断顺序，因此写入文档注释并由测试钉住。
5. **Core 引入 `glam` 作为唯一数学依赖。** 该决策只改变 Core 的依赖清单，不改变边界含义：Core 仍不依赖 wgpu、winit、egui、浏览器 API、平台路径或第三方 glTF 类型。
6. **旧入口与死代码一并删除**：`parse_first_mesh_primitive`、拥有式 `MeshInstance`、无调用者的 `GpuState::set_mesh` 与 `ObjectBinding::update`；`glam` 从 `scenescope-gltf` 的依赖中移除。

## 实施记录

2026-10，迁移落地：

- **Core**：新增 `mesh_instances` 与 5 条单测（根节点声明序、深度优先与子节点顺序、共享节点只访问一次、父子变换组合、无默认场景）。
- **glTF 适配器**：删除旧入口、三个随之失效的错误变体（`MissingMeshPrimitive` / `MissingScene` / `MissingMeshNode`）与 `find_first_mesh_node`；`glam` 依赖移除，适配器只剩格式转换职责。
- **Renderer**：`GpuState` 与 `MeshBuffers` 改为接收 Core 的实例视图；`set_mesh` 与 `ObjectBinding::update` 删除（无调用者）。
- **平台入口**：desktop 与 web 都先解析 `AssetDocument`，再派生实例创建 GPU 状态。"只绘制第一个实例"是临时策略，在两处以同一注释标记，待 M2-004 替换。
- **证据**：`cargo test --workspace --all-targets` 21 个测试通过（Core 7 / glTF 10 / Render 4）、`cargo release-check`、`cargo fmt --all --check`、wasm32 目标编译通过；桌面端画面与 M1 截图一致，即迁移未改变像素。

## 考虑过的选项

- **保留两个解析入口**：拒绝。不变量需两处同步，与 v0.1 的多节点/多 primitive 范围也不符。
- **渲染器自行遍历节点树**：拒绝。这会把资产语义（节点层级、变换组合规则）放进渲染层，将来的统计与规则检查还要再实现一遍。
- **Core 手写矩阵数学（不引入 glam）**：暂缓。Core 保持零依赖有价值，但手写四元数→矩阵与 4×4 累乘是关键路径上的新风险；若要做，应先以 glam 为参照实现交叉验证测试，而不是在迁移中顺带改数学。
- **让渲染器直接接收 `&AssetDocument`**：拒绝。渲染器将被要求决定"绘制哪些实例"，而它当前只能绘制一个——接口会表达一个它并不具备的能力。
- **返回 `Vec<&MeshInstance>`**：不可行。文档并不存储实例值，且遍历中构造的实例是局部值，无法借出。
- **让文档缓存实例（`Vec<MeshInstance>`）**：拒绝。实例是派生数据，缓存引入失效管理成本，而按需计算的成本可忽略。

## 后果

好处：

- 数据流唯一：`bytes → AssetDocument → 实例视图 → GPU`，不再存在两份几何或两种模型。
- 适配器只剩格式转换职责（并因此不再依赖数学库）；世界变换只在 Core 实现一次，统计、规则与界面将来直接复用。
- 实例视图零拷贝：同一 mesh 被 N 个节点引用时只存 N 份（指针 + 矩阵），而不是 N 份几何。

代价：

- **实例的生命周期绑定到文档**：调用方必须保证 `AssetDocument` 活得更久；在临时值上调用 `mesh_instances()` 会被借用检查器拒绝。
- Core 从"零依赖"变为"依赖 glam"，依赖清单纯净度下降（平台与格式边界语义未变）。
- 渲染器当前仍只绘制第一个实例；多实例绘制、纹理采样与材质绑定留待 M2-004。

## 重新评估条件

- M2-003 引入运行时换资产时，重新设计文档所有权与 GPU 资源重建策略（原先为此准备的 `set_mesh` 因无消费者已被删除）。
- M2-004 实现多实例绘制时，评估渲染器是否应直接接收实例切片，以及"绘制哪些"这一策略的归属。
- `glam` 升级到大版本（当前 0.34.1）或 Core 出现第二个数学依赖时，重新评估数学层归属。
- M4 的 benchmark 证明场景遍历或实例分配成为瓶颈时，考虑改为惰性迭代器（避免为取首个实例而构建完整列表）。
- 若将来需要处理超大型资产，重新评估"几何拥有在文档中"这一前提（可能转向对 GLB 字节的借用视图）。
